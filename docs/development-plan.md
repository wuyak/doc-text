更新：2026-09-15。本文统一记录 doc-text 的目标、已确认行为、实现要求和验收依据。项目已从 legacy-doc 二开 worktree 迁为独立子目录和 Git 仓库；保留纯 Python、零运行时依赖和最小文字提取范围。

状态：消融审计中的冗余清理及三项最小修正均已按用户要求完成，最新验证为 277 项测试通过、200 份语料完整结果不变，见第 10.5、10.6 节；现有资源上限及错误返回方式见第 10.7 节。第 8 节的根存储选流与嵌入占位、容器长度、制表位三项均已实现，实现验证见第 7.7 节。第 9.3 节“外层单元格以内表开头”已完成，见第 7.6 节。其余段落、表格和文本框问题仍按第 9 节分别处理。

## 1. 目标、范围与公开行为

在 `legacy-doc` 内补齐规范文字定位、正文选择、段落及表格识别、文字拼接，使提取结果遵循已选定的 DOCX 文本规则。保持纯 Python、零运行时依赖，复用现有 OLE 读取和元数据能力。

本方案只涉及独立文字提取库。平台已有 DOCX 函数作为固定的输出参考；平台接入、提示链路、界面文案和提示类型留待后续另行设计，不属于本次实现或验收范围。DOCX 参考源码不成为库的运行时依赖。

以下决定已确认：

- **统一替换底层。** 所有入口使用 FIB 指定的文字记录，不保留旧 CLX 扫描路径。
- **默认直接使用新输出。** 现有 `extract_text()` 调用直接返回本方案定义的结果，不增加切回旧文字压缩行为的开关；不引入此前讨论的多模式选项。
- **沿用结果类型。** 继续返回 `DocExtractionResult`，使用现有 `text`、`metadata`、`warnings` 等字段，不新增公开的 Word 文档或表格对象模型。
- **合法空正文返回空字符串。** 按本方案选择和拼接后没有文字时，返回 `text=""`，不将它当作文件损坏，也不把提示文案填入正文。
- **影响所选文字完整性的损坏使整体失败。** 不将残缺文本作为成功结果；所读取的可选元数据损坏沿用 warning。元数据只解码实际返回的字段及码页，其他属性仍检查索引范围。
- **嵌入文件只在正文占位。** 识别所选正文中的嵌入文件对象，在原位置输出名称、类型或通用占位；不解析附件内部内容、不递归、不另发提示。对应 `EMBED …` 指令由占位替代。具体规则及命名边界见第 8.1 节。

这次改变会影响旧调用方实际得到的文字：恢复表格分隔、保留主体空段落和连续空格、排除未选文档部分，并停止按 PAGE 字样删除所选正文内容。发布说明应明确记录这些变化；调用函数和结果载体不因此另建一套。

## 3. 二进制解析与输出设计

### 3.1 按 FIB 定位文字，保存字符与字节位置

| 规则 | 对实现的要求 | 官方依据 |
| --- | --- | --- |
| FIB 记录版本及后续结构位置 | 校验签名、计数和有效版本；考虑 nFibNew 的覆盖；按支持版本解释结构 | [Fib](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/9aeaa2e7-4a45-468e-ab13-3f6193eb9394)、[FibBase](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/26fb6c06-4e5c-4778-ab4e-edbf26a545bb) |
| fcClx/lcbClx 指向 CLX | 在对应 0Table/1Table stream 中按指定偏移和长度读取，解析 RgPrc 与 Pcdt/PlcPcd | [取文本算法](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/01d5d8c4-cf9c-4ef9-80fd-439e763cfe01)、[Clx](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/bad26767-b575-44d3-9da3-96378d56ce14) |
| CP 是文档字符位置，FC 是存储位置 | 保留两者映射，按 CP 顺序处理，不能按物理地址排序文字 | [取文本算法](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/01d5d8c4-cf9c-4ef9-80fd-439e763cfe01) |
| 压缩/非压缩 piece 的位置和宽度不同 | 压缩位置值先除以 2，每 CP 一字节；非压缩每 CP 两字节；内部 FC 统一为实际字节偏移 | [FcCompressed](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/aa2e55a2-f4f2-4795-bab5-6d9d7a0ed249) |
| cbMac 限定有效 WordDocument 内容 | 对该 stream 的文字和结构引用同时检查 cbMac 与实际长度；Table/Data stream 各自按自己的长度检查 | [FibRgLw97](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/37713d3c-a0c8-40f5-821f-bc9622c7de48) |

基线代码用作 fc_min/fc_mac 的 FIB 0x18、0x1C，在所依据规范中是未定义保留字段。新实现不能继续用它们判断哪些文字有效。Word 6/95 不在本次新增支持范围内；支持版本的清单和各版本长度条件要写进源码测试，不能只使用“版本大于某值”这样的宽泛判断。

建议使用小型私有记录保存信息：

- `FibInfo`：有效版本、所用 Table stream、cbMac、各文档部分的长度及定位阶段需要的结构位置。
- `Piece`：`cp_start`、`cp_end`、实际字节偏移 `fc`、压缩标志和 `prm`。保留 PRM 供后续段落属性解析使用。
- CLX 属性组：保存 Prm1 后续引用所需的 Prc 内容及索引关系。
- 区间读取能力：输入合法 CP 半开区间 `[start, end)`，与各 piece 求交后定位字节；选择哪个区间由调用方决定。

字段名为实现建议，不构成新的公开 API 承诺。

文字读取应遵守：

1. 非压缩文字在定位阶段按 UTF-16 的 16 位单元计数，不能拿 Python 字符串长度当作 CP 数。
2. 先计算区间和结构位置，再解码；不能先清洗字符串后据其长度回推原文件位置。
3. 保留跨 piece 的有效代理对，正确读取 emoji 等非 BMP 字符；不能分别使用替换解码后再拼接，造成有效字符丢失。
4. 压缩文字按 MS-DOC 指定映射解释。对于位于文本范围内但不显示的控制符，定位阶段保留其值，交给后续结构和清洗步骤处理。
5. 不在定位阶段合并空格、删除 PAGE 字样、解释字段结果或改变段落分隔。

### 3.2 选择正文，并关联另存的正文文字

| 内容 | DOCX 当前行为 | DOC 需要对应的行为 |
| --- | --- | --- |
| 主体段落、表格 | 读取主体中的段落与表格文字 | 从主文档字符范围读取，并恢复段落、表格关系 |
| 独立页眉、页脚 | 不打开对应 XML | 不提取 header story；页眉中的文本框也不纳入 |
| 独立脚注、尾注、批注 | 不打开对应 XML | 不提取对应 story 的说明文字；正文中的普通字面内容不因此删除 |
| 正文文本框 | 递归可达的文字节点会被读取 | 按正文形状锚点找回文本框内容，不能仅截取 `ccpText` 后就宣称完成 |
| 字段代码及结果 | `instrText` 与 `t` 都读取 | 普通字段保留已存储的代码和结果文字；不计算字段，不只取结果，不正则删除 PAGE。已确认的嵌入文件对象按第 8.1 节以占位替代 |
| 插入、删除修订文字 | `t` 与 `delText` 都读取，不检查修订状态 | 保留目标正文范围内已存储的相应文字，不主动接受或拒绝修订 |
| 隐藏文字 | 不检查文字的隐藏属性 | 不因 `CFVanish`、`CFFldVanish` 等显示属性过滤已选文字 |
| 图片、外部对象 | 不做 OCR，不跟随外部关系提取对象 | 不因图片或对象存在而增加 OCR、联网或附件解包流程 |
| 嵌入文件对象 | 原参考行为不承诺生成文件占位 | 用户明确新增的 DOC 输出规则：只识别对象及可用名称/类型，在正文原位置占位，不提取内部文件内容 |
| 艺术字 | 可达的 `t` 节点会读取；仅在属性中的字符串不会读取 | 必须核对具体存储形式，不能把所有艺术字概括为“全取”或“全不取” |

这里的“正文”是提取范围，不能简单等同于 DOC 规范中的 main document story。后者是 DOC 的一个连续字符区间，正文文本框通常另存。微软明确规定主文档范围为 `[0, ccpText)`，并包含指向其他内容的锚点。[Main Document](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/f426d9a2-004d-418e-8d8c-e7fd88e7c48e)、[Textboxes](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/f87b3560-2c23-4d10-9751-ff141d307308)。

1. **主体范围。** 从 FIB 读取 `ccpText` 等各 story 长度，按规范确定字符区间；正文、文本框的 CP 不能混用各自的局部坐标。所有加法和引用在读取前检查边界。[FibRgLw97](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/37713d3c-a0c8-40f5-821f-bc9622c7de48)。
2. **正文形状与文字。** 读取正文形状锚点，关联 OfficeArt 形状标识与文本框记录，再读取对应文本框区间。按锚点的正文位置加入内容，不能把所有文本框统一追加到文末。未被正文引用的闲置文本框记录不得顺带输出。[PlcfSpa](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/e98fe93c-d57f-4d9b-a519-30e6acbdd414)、[PlcftxbxTxt](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/9f17f89a-64d6-4546-a811-e62e1d238102)、[FTXBXS](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/d0a81fe8-f9e8-4130-9233-84732e3d9420)。
3. **普通文字与控制记录。** 字段边界和对象锚点不能作为可见字符直接输出；也不能删除它们附近的普通文字。必要时使用字符属性 `CFSpec` 识别特殊字符。读取结构标记与过滤字段代码是两回事。[字符属性读取](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/be58bf9c-d1d3-40cc-91ee-36452d7939b2)、[Fields](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/751b09bb-72f0-45ef-8e87-666dea68219f)。

实现时需把关联落实为可检查的字段：FIB 的 `fcPlcfSpaMom/lcbPlcfSpaMom` 定位正文锚点；`fcPlcftxbxTxt/lcbPlcftxbxTxt` 定位文本框范围；使用 `SPA.lid`、OfficeArt 的 `spid`、`FTXBXS.lid` 关联形状；核对 `lTxid` 高 16 位所指的 FTXBXS 一基索引。`fReusable` 槽及最后的特殊记录不能当作实际文本框输出。只解析所需标识和引用，不计算几何位置及绕排。[lTxid](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-odraw/6f50606e-9a41-4555-961f-95317c8ed15c)。

字段指令、结果以及标为删除修订的文字仍存于所属 story，通常不需要另找文字内容。字段位置表描述边界，不代替文字片段；输出消费 `0x13/0x14/0x15` 等结构标记，保留普通字段中已存储的文字。嵌入文件对象是明确例外，以一个正文占位替代对应内部指令及对象标记，不重复输出。`CFSpec` 表示特殊含义，不是隐藏开关。[Character Properties](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/7022285b-9621-42e9-ad4d-4e02c115ef18)。

### 3.3 读取段落属性，恢复行、格和嵌套关系

DOC 的第一层表格用特殊段落标记区分格与行；嵌套表格还要结合层级属性。段落可能跨 piece，应找到真实结尾，再读取适用属性。仅把 `0x07` 换成 TAB，无法判断哪一处应结束外层单元格或表格行。[Tables](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/5b45f0e7-7760-4fdb-af88-0146de2feb4c)、[段落边界](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/30461a5b-e3ad-44cd-a3fe-038f86639b13)。

1. 从 FIB 的 `fcPlcfBtePapx/lcbPlcfBtePapx` 定位段落属性索引，再定位 512 字节 PAPX FKP 页。遇到正文 `0x0C` 时，结合 `PlcfSed.aCP` 区分分节结束与段内手动分页；后者只在段内变成 LF，不先拆段后清理两侧空格。[PlcfSed](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/68a959a6-11e0-4f3e-9a99-76ca8cc4dddc)。
2. 找到段落结尾对应属性，读取 PAPX，再按规范应用结尾 PCD 的 PRM 修改。不能假设首个 piece 的属性代表整个段落。[直接段落属性](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/61b635c3-2c44-4155-bf17-fec281b30c71)。
3. 至少识别 `PFInTable`、`PFTtp`、`PItap`、`PDtap`、`PFInnerTableCell`、`PFInnerTtp`。`PDtap` 是有顺序的层级增量，不能把属性简单存入字典后只保留最后一个值。[段落属性](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/484822ee-a9d9-4af4-8423-29fda67a6a58)。
4. 支持 Prm0 的相关简短属性及 Prm1 指向的 CLX 属性组。遇到 `PHugePapx`、`PTableProps` 等间接属性时，按规范读取 Data stream；遵守替换和应用顺序，限制引用深度、循环和总处理量。
5. 跳过不需要的属性时，仍按 SPRM 的真实操作数长度前进，处理可变长度例外，不能按固定长度猜下一条。PAPX 字节数按 `PapxInFkp` 解释，不无条件吞掉末尾孤立字节。[Sprm](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/099eb99c-a927-4caf-a80c-66254ea83d6a)、[PapxInFkp](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/580510b8-df7a-467e-a51c-0d71eb15c7cd)。

内部使用段落、单元格、行的小型记录保存这些关系。

DOC 的物理单元格边界不能直接视为 DOCX 的 `tc` 数量。平台对直接 `tc` 逐个输出，对 `gridSpan`、`vMerge` 不展开、不复制文字。

| 情形 | 平台基准 | 对 DOC 实现的要求 |
| --- | --- | --- |
| 普通两格 | `A\tB` | 依据行、格结束建立两个输出格 |
| 一个 `tc` 跨两列，后跟另一个 `tc` | `A\tB` | 不为跨列跨度补空格；需确认 DOC 的合并记录如何对应这个 `tc` |
| 垂直合并首行为 A/B，次行续格为空/C | `A\tB\n\tC` | 不复制上方 A；保留前置空格子的分隔，随后按拼接规则清理行尾 |
| 一个 `tc` 含嵌套表格 | 后代段落用 LF 拼接 | 内层单元格不产生外层 TAB，不额外输出内层行结束标记 |

需要读取表格定义及适用的合并属性，而不是仅靠 `0x07`。规范给出了 `TDefTable`、`TInsert`、`TDelete`、`TMerge` 与单元格属性；实际 DOC 记录的单元格、合并区域和最终输出格需要明确映射。[表格属性](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/b39a6648-501c-4361-8366-4f042f579469)、[TDefTableOperand](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/de06ec41-a0ac-4046-9096-cdfaa0091ad9)、[TC80](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/9dd62a79-8c0b-4b11-99ee-05742ae7cf6d)。

跨格式表示本身可能不同：DOCX 也可能以多个带合并标记的 `tc` 表示一个区域，而平台会照读这些 `tc`。因此“画面一样”不够作为逐字相同的验收条件。对每种声称支持的映射，必须提供结构明确的配对 fixture，不能由某个转换器输出反推唯一规则。

已核对的 DOC 细节：`TCGRF.horzMerge=1` 表示横向合并续格，`2/3` 表示首格；`sprmTMerge` 也可给出横向合并。纵向合并的续格仍计入物理格索引。横向合并会改变输出格分组，须应用后续有效行属性，不能只读取初始 TC80。2026-09-15 经用户确认的消融清理后，不再保存和传播不参与输出的纵向合并状态；`sprmTVertMerge` 仍检查记录长度、标志取值和单元格索引，正文继续按物理格及其已存文字提取。[TCGRF](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/11bf5b1c-943f-421d-bbf3-39088cd1b8dd)、[VertMergeOperand](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/cf7489ac-7eee-404d-8844-8ebbd279b77d)。

规范中“续格的内容不渲染”不能单独作为删除文字的依据，因为平台也不按可见性过滤 DOCX 文字。遇到续格含字的样例，应先确认其合法性和对应的 DOCX 存储，再确定输出；不能直接将所有续格内容强制清空。上述垂直合并基准只针对内容为空的续格。

嵌套表格最终按所属单元格内的后代段落展开，不输出独立的内层列分隔。仍须维护嵌套层级，以免把内表结束误当作外表结束。

### 3.4 按固定规则拼接文字

对已建立对应关系的 DOC 内容，输出按以下顺序构造：

1. **段落内文字。** 按读取顺序拼接文字、普通字段代码和结果、修订文字，以及第 8.1 节规定的嵌入文件占位；TAB 保留为 `\t`，手动换行对应 `\n`。平台把 `br` 和 `cr` 都当换行，包括有 page/column 类型的 `br`。DOC 中分页、分节及对象特殊标记须先按格式识别，不能把所有控制字符都当普通换行。
2. **清理单段文字。** 使用 `text.replace("\r\n", "\n").replace("\r", "\n").strip(" \n")`。只去首尾空格和 LF；保留内部连续空格、TAB，以及没有被对应 XML 读取规则排除的普通 Unicode 字符。
3. **单元格。** 按对应的后代段落顺序，过滤清理后为空的段落，用 LF 拼接剩余段落。嵌套表格按段落展开。
4. **顶层表格行。** 单元格用 TAB 拼接，再调用不带参数的 `.rstrip()`。它去除行末所有 Python 空白字符，包括末尾空单元格留下的 TAB；不清理行首 TAB。
5. **整篇正文。** 顶层段落和顶层表格行按顺序用 LF 拼接。中间空段落、空行保留位置；最后再执行第 2 步的 `_clean_text()`。

DOCX body 的其他包裹节点走的是“枚举后代段落”分支，不会再次套用顶层表格行列序列化。DOC 若有可对应的内容容器，必须先确认结构对应，不能假定所有表格都天然获得顶层 TAB 规则。

基线 `normalize.py` 的全局正则会合并连续空格和 TAB、删除空行、删除 PAGE/NUMPAGES 字段文字、过滤私用区字符及 U+FEFF。这与基准不一致。新的对齐输出路径需要移除这些清洗步骤，以选定的内容范围和结构记录决定输出。

例如字面正文 `A  B` 的两个空格应保留；一个实际字段中存储的 ` PAGE ` 和结果 `3`，在该段首尾清理后是 `PAGE 3`。不会为了让结果更像 Word 画面而自行隐藏字段代码或修订删除文字。

DOC 结构控制符需要消费，而真实文字需要保留。不能为了停用旧清洗就把 `0x07`、字段边界、对象锚点直接写进文本，也不能继续按全局字符黑名单删除本可对应到 XML 文本的字符。

### 3.5 区分格式映射与视觉相同

可直接比较的是明确对应的内容和结构。对同样的主体段落、表格和字段构造各自合法的 DOC、DOCX 样例，先确定 DOCX 基准文本，再检查 DOC 输出。不要把某个转换器生成的所有 XML 细节当作 DOC 规范保证。

平台遍历还存在两种必须单独记录的行为：

- 正文段落内的文本框有两段“框一”“框二”时，递归 inline 读取会得到 `前框一框二后`，不会为框内段落自动加换行。
- 同样的文本框放在表格单元格中，父段落和后代段落都会被读取，可能得到 `前框一框二后\n框一\n框二`。这是已验证的遍历重复，不能把“保持可见文字一致”与“逐字复制当前输出”混为同一个承诺。

目前的决策是沿用平台逻辑，因此文档保留这些基准结果，不在此次 DOC 设计中顺带修正平台。如何把 DOC 的锚点和独立 story 投影成相同的遍历关系，仍需合法样例验证；未通过前，不能宣称文本框完全对齐。

艺术字也是表示形式的边界：DOC 的 OfficeArt 可以把文字存入 `gtextUNICODE_complex`，而 DOCX 的文字可能成为元素文本，也可能成为 VML 属性。相同画面不保证相同基准输出。确定实现范围前需记录实际对应形式；不能自行扩大为“解析所有 OfficeArt 字符串”，也不能把可读取文本框和艺术字一概排除。[gtextUNICODE](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-odraw/3b9a1a7b-ad49-410c-bb32-ab91decff765)、[实际 Unicode 字符串](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-odraw/c2dfbfd1-9652-40c2-a8d2-1f292bae61b5)。

## 4. 损坏、兼容与资源边界

| 情形 | 结果 |
| --- | --- |
| 所选内容按规则拼接后为空，所需结构合法 | 成功返回 `text=""` |
| FIB 指定的 CLX 缺失、越界或结构不成立 | 整体失败；不扫描其他候选记录回退 |
| 必需 piece、字符范围或编码损坏 | 整体失败，不静默跳过，不以替换字符掩盖已确认的文字损坏 |
| 已选正文或已引用文本框的必要关联、段落或表格结构损坏 | 整体失败，不返回文字或顺序不完整的成功结果 |
| 未选 story 的独立内容损坏 | 不主动解码或深入验证；确定所选内容所需的共享记录仍须合法 |
| 可选标题、作者等元数据损坏 | 正文可读时继续，沿用 metadata warning |
| 加密、不支持的版本、资源超限 | 给出可区分的错误原因，不一律称为文件损坏 |

严格读取不等于实现完整 DOC 验证器。校验所选内容依赖的结构，尊重必须忽略的保留字段。规范允许的写入差异应在同一路径内处理，不通过恢复旧扫描兼容。过去靠扫描碰巧读出的文件可能报错，这是已接受的兼容代价。

Word 提供恢复损坏文件的路径，因此“某个应用能打开”只能作为兼容线索，不能证明所有记录符合规范；库不承担文件修复。[微软文件修复说明](https://support.microsoft.com/en-US/Word/open-a-document-after-a-file-corruption-error)。

保留现有最大文件、stream 和输出限制。读取及分配前检查偏移、长度、计数和加法边界；按增量检查输出 UTF-8 大小，不能只在完整大字符串生成后检查。对重复 piece 引用、文本框引用、嵌套表格和间接属性设置有界处理，防止异常工作量及循环。文字结构预算不能借用语义无关的 OLE 链长度选项；具体内部阈值仍需依据规范和样例确定。

单元格结束、行结束和嵌套层级须相互一致；检查行格数、合并范围时应读取相应表格定义。不能仅凭基础层级标记就宣称完成全部表格一致性校验。

### 8.1 主文档数据选择与嵌入文件占位

主文档的 `WordDocument`、FIB 指定的 `0Table/1Table` 和所需 `Data` 必须按所属根存储读取，不能在整个 OLE 目录中按名称取首个匹配项。嵌入文档可能拥有同名数据流；即使主文档某项缺失，也不能拿嵌入文档的数据代替，或扫描候选流寻找能解析的记录。

只识别所选正文中嵌入文件对象的存在及可可靠读取的描述信息。文件内容不解码，不调用 Excel、TXT、PPT、PDF 或其他文件解析入口，不递归处理嵌入对象；允许有界读取识别和命名所需的对象元数据。仅有嵌入对象不会使合法主文档整体失败。

在对象对应的正文位置输出：

| 能可靠取得的信息 | 正文占位 |
| --- | --- |
| 文件名及其已有后缀 | `[嵌入文件：报价表.xls]` |
| 只有对象类型 | `[嵌入文件：Excel 工作表]` |
| 名称和类型均不可得 | `[嵌入文件]` |

不根据内部存储编号伪造文件名，不根据猜测补后缀。占位替代对应 `EMBED …` 内部指令及对象标记，一个对象位置只输出一次；不另发 warning、提示或把占位统一追加到文末。缺少可选名称/类型时使用上述回退，不为补名称而解析附件。普通图片、外链和字面正文中的 `EMBED` 单词不因字符串匹配自动变为嵌入文件占位。现有可选元数据损坏规则不因此取消。

示例：`具体报价请参考以下附件：\n[嵌入文件：报价表.xls]\n付款方式另行协商。`

命名边界：按 [Plcfld](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/751b09bb-72f0-45ef-8e87-666dea68219f) 的 EMBED 类型和特殊字符定位，再按 [ObjectPool](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/f7983581-d107-4a1f-b5f7-f3650e777c04) 的规则关联存储。对象类型取 [CompObjStream](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-oleds/142e0420-2f74-4ed9-829b-0b3d5a684d01) 的显示名称，支持明确的 UTF-16 类型名；ANSI 字符串只接受无编码歧义的 ASCII。当前文件名读取限于已标识的 Package/Package2 对象及其 Ole10Native 头中的 ASCII 文件名，保留已有后缀并去除路径。元数据前缀每次最多 4096 字节，未知编码或原生格式回退到类型/通用占位；上面的中文文件名是输出约定示例，不表示已实现任意旧代码页的中文文件名读取。

Microsoft 的 MS-OLEDS 将 NativeData 留给具体应用定义，没有统一文件名结构；此处 Package 头布局参考 [Apache POI 的固定源码](https://apache.googlesource.com/poi/+/0614835c55f44ab6f3e9b0850ca51e0e53a65a49/poi/src/main/java/org/apache/poi/poifs/filesystem/Ole10Native.java)，不把它冒充所有嵌入对象共用的微软格式。不执行、展开或解释头部之后的附件载荷。

此占位是用户明确新增的 DOC 输出约定，不要求修改平台 DOCX 提取器。上游若断言嵌入文件内部的文字，须改写为我们的主文档及占位断言，不能照搬递归提取预期。`Bug47731.doc` 的上游稻米句子位于嵌入 Word 中，故不属于我们的正文验收条件。

已验证：根/嵌入同名流的目录枚举顺序不影响主文档输出；有名称、仅有类型、信息缺失三种占位均覆盖；正文、单元格中位置正确；原 `EMBED` 指令不重复输出；附件内容及更深层附件均不读取；主文档缺失必要流仍拒绝。真实回归包括 `53379.doc`、`Bug47731.doc`、`Bug50936_3.doc`、`Bug61268.doc`、`word_with_embeded.doc`。其中其他独立结构问题须单独验收，不能因为根流选对就称全文提取正确。

### 8.2 按容器版本解释长度

MS-CFB Version 3 使用 512 字节数据块，stream 长度按低 32 位解释，兼容旧实现未初始化的高 32 位；Version 4 使用 4096 字节数据块，按完整 64 位解释。应核对版本与数据块大小的合法组合，然后按真实长度执行现有文件、stream、链和输出限制；不提高资源上限，不把所有版本统一截成 32 位。[MS-CFB 目录项长度规则](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cfb/b37413bb-f3ef-4adc-b18e-29bddd62c26e)。

### 8.3 按官方宽度解析制表位记录

### 9.1 段落属性后多出一个零字节

场景：正文由普通段落组成，但某个段落的格式记录在完整指令之后又多出一个零字节；用户看见的文字并不一定异常。`test.doc` 的相关属性字节为 `31 24 00 00`，前三字节组成完整 SPRM，最后一字节触发“孤立 SPRM 字节”。POI 对该文件有 24 个段落及连续 `as d` 文字的断言。

官方 `PapxInFkp` 对普通和扩展长度分别给出确定公式，当前读取公式与其一致；`GrpPrlAndIstd.grpprl` 明确要求由完整的 Prl 元素组成。未找到允许在该数组内部附加任意一个零字节的规定，不能把它直接称为合法填充。[PapxInFkp](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/580510b8-df7a-467e-a51c-0d71eb15c7cd)、[GrpPrlAndIstd](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/bd96f2aa-1318-4066-9723-4db035ef412b)。

建议：在没有更具体的版本例外或读取错误证据前，保留拒绝，归为“段落属性记录不完整”。若以后决定容错，应仅接受已证实的特定末尾形式，并验证后续属性和正文；不能全局跳过孤立字节。此前将此例优先建议修复的判断，现因规范证据收紧。

### 9.2 首段文字与格式索引的位置对不上

场景：文字本身能定位并解码，但查询这段文字的段落属性时，索引指向的格式页不覆盖它。`Bug48075.doc` 首段末尾 CP 为 13、字节位置 FC 为 2074；对应 BTE 范围从 2048 开始，FKP 页的 FC 却从 4096 开始。POI 验证首段以 `Приложение` 开头，本机隔离转换也读出该标题，但都不能证明默认段落属性就是正确恢复方式。

进一步核对：首个 piece 为 CP `[0,1199)`、FC 2048、`fCompressed=0`，因此 CP 13 的正确物理位置就是 `2048+13*2=2074`；该位置确实保存 UTF-16 段落标记 `0d 00`。后续多个页也出现 BTE 起点 2240/2448/2449 对应 FKP 起点 4480/4896/4898 的二倍关系。已排除我们把这个未压缩 piece 错按压缩文本换算的解释，文件中的两组索引存在系统性不一致。[取文本算法](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/01d5d8c4-cf9c-4ef9-80fd-439e763cfe01)、[FcCompressed](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/aa2e55a2-f4f2-4795-bab5-6d9d7a0ed249)、[直接段落属性](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/61b635c3-2c44-4155-bf17-fec281b30c71)。

建议：按“段落属性定位不一致”保留拒绝。目前没有微软对这种二倍坐标形式的合法例外，不能把 FKP 坐标全局除以二，也不能对索引空洞套用默认属性；否则可能破坏正常文件或丢掉表格成员、单元格和行结束信息。若将来要容错，需要另外证明有界修正后的全部索引、段落及正文预期一致；仅成功读出标题不够。

### 9.3 表格层级跳跃与结束标记缺失

典型场景是外层单元格的第一个内容就是内层表格：按正文顺序读取时，可能先遇到内层段落，之后才遇到外层单元格的结束标记。不能只凭“前一段深度为 0、下一段为 2”就断言文件损坏；必须检查后续是否存在完整的外层单元格及行。

官方定义：第一层单元格以 `0x07` 结束；更深层单元格以 `0x0D` 加 `PFInnerTableCell=1` 结束。行结束还须有相应的 `PFTtp` 或 `PFInnerTtp`，行定义的格数须与实际格数一致。深度来源为直接段落属性 `PFInTable/PItap/PDtap`。[表格结构规则](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/5b45f0e7-7760-4fdb-af88-0146de2feb4c)。

| 样本 | 目前观察 | 需要区分的情况 |
| --- | --- | --- |
| `fdo53985.doc` | 普通段落后直接出现深度 2 的单元格；后续内层及外层格/行结束均存在，行定义数量闭合 | 已按允许以内表开头的结构修正，完整正文断言通过，见第 7.6 节 |
| `Bug51890.doc` | 一层表格结束后直接遇到深度 3；67 条段落记录可按三层容器闭合，格、行及行定义均匹配 | 同一缺口已修正，关键正文及顺序断言通过，见第 7.6 节；上游图片测试本身仍不作为正文预期 |

处理条件：能按官方规则恢复完整层级时，修正过严的进入顺序检查；真实缺少结束标记或行格定义时，保留拒绝。不得猜测插入 TAB/LF，也不把全部表格压成普通段落以掩盖失败。

### 9.4 文本框存在，但缺少规范关联编号

`Bug53380_1.doc` 在正文 CP 3 有 shape 1027 的锚点；形状、FTXBXS 文本记录和 ClientAnchor 都能对应，文本框范围也有界。但逐条检查 OfficeArt 后确认：既没有 F00D `OfficeArtClientTextbox`，FOPT 中也没有 `opid=0x0080` 的 `lTxid` 属性，不是已存在记录被读错位置。

此例的文本框内容实际为 `EMBED MSPhotoEd.3` 字段及控制符，指向嵌入 Photo Editor 对象，不能描述为“丢失了一句普通文本框文字”。即使未来能规范关联，也应按第 8.1 节生成嵌入文件占位，不解析对象内容。

建议：该样本目前保留“文本框必要关联信息缺失”的拒绝，不因为形状 ID 恰好唯一就跳过规范要求。另有独立实现问题须核查：当前代码主要从 F00D 取文本编号，FOPT 的规范 `lTxid` 读取及一致性检查未落实完整；补全这项检查不等于该样本会成功。本轮原始记录审计补充确认：`Bug50936_1.doc` 的 shape 1151（正文 CP 14624、FTXBXS index 11）和 `Bug61268.doc` 的 shape 4280（正文 CP 46080、FTXBXS index 66）也均缺少 F00D 与 FOPT lTxid，虽各自有对应的 ClientAnchor 和 FTXBXS。`Bug61268` 其他形状存在 481 对这类记录，可排除扫描器完全找不到记录的解释。补读 FOPT 不能直接修复这三个目标形状。建议依当前严格关联规则保留拒绝，但本次简审不能证明其来源必然是人为构造的坏文件，也没有穷尽旧式或替代表示。

| 文本框关联、字段索引和附件元数据前缀读取 | 无法保证锚点顺序、所选文字完整性和附件只占位；字段与引用边界不是可任意跳过的格式信息 |
| 文件/链限制、解析工作量和最终输出限制 | 三者限制不同资源。很小的输出可能需要处理大量控制记录，输出上限不能替代输入及遍历限制；底层限制也不能替代最终 UTF-8 字节数检查 |
| 已承诺的元数据与 warning、针对异常输入的测试 | 这些仍属于既定结果接口与失败行为，不能因为正文不依赖它们就直接删除 |

不建议为减少文件数合并解析模块，也不建议只为减少用例数删除测试。真实文件的正文断言、合成边界反例和批量运行分别回答不同问题；200 份批量返回状态仍不等于 200 份全文准确性断言。

### 10.3 发现的问题与处理优先级

**验收前建议补齐选中文本框的失败边界。** `_shapes.py:476–489` 接受实际锚点 CP 等于 `ccpText`，关联后加入选中文本框集合；`_text.py` 只遍历 `[0, ccpText)`，因此不会消费这个锚点，也不会执行该锚点的字符检查。完整 OLE 反例的正文是 `前后\r`（长度 3），CP 3 指向已关联、含 `框内文字` 的文本框，公开入口却成功返回 `前后` 且没有 warning。这不是正常样本兼容扩展，而是已选择的结构没有被处理却报告成功。建议在渲染前或结束时核对选中锚点能否被消费；不满足正文范围、`0x08` 和 `CFSpec` 条件时明确失败。微软的 FIB 字段允许 CP 不大于 `ccpText`，但实际形状锚点又要求字符及属性匹配，因此不要简单把通用 PLC 上界全部改成严格小于。[PlcfSpa 锚点要求](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/e98fe93c-d57f-4d9b-a519-30e6acbdd414)。本轮没有发现对应的真实文件，问题由构造反例证明。

**另有一处选中结构的宽松处理。** `_paragraphs.py:903–923` 在没有有效表格成员属性时，将 `0x07` 当作普通段落结束。无表格属性的 `A\x07B\r` 通过公开入口返回 `A\nB`。建议补明确拒绝，或先证明这种组合属于合法表示再保留；当前没有后者的依据。该反例没有丢掉 A/B，但会把无法确定的表格关系变成普通换行，弱于既定的严格失败要求。

**整理验收脚本的分类。** `scripts/check_corpus.py:34` 只用 `exceeds parser limit` 这一短语识别资源超限。构造超过默认 25 MiB 上限的文件后，解析器正确报 `.doc file exceeds parser file-size limit`，报告却归为 `rejected-needs-review`；输入工作量和遍历工作量的不同文案也会漏分。这是报告分类问题，未发现因此放行超限文件。建议收拢资源错误的识别条件，不必为此新增一套异常框架。第 9.6 节的审计处理结论目前也仍与批量运行分类分开保存，不能把脚本退出码当作已确认范围的完整验收结论。

**目录名称有两处低优先级的严格性缺口。** `ole.py:293–301` 没有核对名称声明范围末尾的 UTF-16 零终止符；`:441–451` 在判断同名歧义前先按对象类型过滤，允许同一父存储下同名的 storage 和 stream。两种人工损坏样本均已复现为接受，正文仍正确返回 `Readable`；本轮没有据此发现正常文件正文误提取。微软要求名称终止且同级名称唯一，建议若补检查，应限制在实际使用的目录名称与查找范围，不扩成完整 CFB 校验器。名称比较须遵循 CFB 的长度及单码元大小写规则，不能直接把 Python `casefold()` 当作完整等价实现。[目录项规则](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cfb/60fe8611-66c3-496b-b70d-a504c94c9ace)、[同级名称比较与唯一性](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-cfb/d30e462c-5f8a-435b-9c4c-cc0b9ea89956)。

独立审查提出的“TC80 数量少于列数就拒绝”已由规范否定：微软明确要求缺项采用默认格式、多余项忽略。当前默认补齐应保留；完整 TC80 记录序列的长度检查也应保留。[TDefTableOperand](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/de06ec41-a0ac-4046-9096-cdfaa0091ad9)。

### 10.7 资源超限的触发条件与返回方式

资源上限用于限制一次提取允许读取、处理和返回的数据量；不是微软 DOC 格式的大小标准，也不单独证明文件损坏。本次只修正验收脚本漏分的错误，未新增或降低解析上限。

| 限制 | 当前默认值 | 触发场景 |
| --- | --- | --- |
| 输入文件及必需 stream 的读取大小 | `max_file_bytes = 25 × 1024²` 字节，即 25 MiB | 传入文件超过限制，或必需 stream 声明的读取大小超过允许范围。例如大量图片使文件较大，即使正文很少，也可能先触发这一限制 |
| 提取文本的 UTF-8 字节数 | `max_text_bytes = 5 × 1024²` 字节，即 5 MiB | 正文、表格分隔和附件占位等按输出规则处理后超过预算。按字节计，不是页数或字数；中文和补充平面字符可能占多个字节 |
| 单条分配链的遍历步数 | `max_chain_sectors = 200000` | 沿 FAT、MiniFAT 或 DIFAT 等链读取时，需要继续访问的块数超过预算。检测到循环、断链或越界则按对应结构错误拒绝，不靠走满预算才发现 |
| 内部处理量及结构容量 | 分别限制，不作为页数或耗时统计 | 多个文字片段反复引用相同字节、大量字段/形状记录或过深嵌套，可能造成处理量远大于最终文字量。达到对应预算时停止处理 |

前三项可由 `ExtractionOptions` 指定。内部二进制解码预算随 `max_file_bytes` 的 4 倍缩放，分别约束一次文字读取累积的 UTF-8 大小以及待解码 UTF-16 缓冲；正文遍历预算随其 8 倍缩放，按字符、拼接及结构操作扣减。它们不是实际内存峰值，也不是毫秒计时。另有具体记录数和深度限制，例如 CHPX/PAPX 页索引 32768 项、OfficeArt 记录 1000000 项、表格或 OfficeArt 嵌套 64 层。

主解析路径触发上限时，公开 `extract_text()` 抛出 `LegacyDocError`，不返回截断正文或成功的 `DocExtractionResult`。可选元数据读取错误仍按既定规则转为 warning；附件名称的有界前缀读取也不意味着解析附件全文。

验收脚本捕获异常后，保留原始文案并返回记录，例如 `{"status": "resource-limit", "error": ".doc file exceeds parser file-size limit"}`。此前同一异常被误分为 `rejected-needs-review`，这次只修正分类。脚本另有每份文件默认 5 秒的子进程超时，分类为 `timeout`；这是批量验证的限制，库函数本身没有默认 5 秒超时。
